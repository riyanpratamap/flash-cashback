# P4.3 code-check: invalidation after commit, demo-reset, harness Redis reset

Reviewer: code-checker (read-only; saved by the main session). Gate re-run by the checker: `make gate` exit=0
(integration 27.5 s); `make test-race` not re-run.

## Answers to the review prompt

- **Delete when nothing committed:** no. The delete in `service/payments.go` / `service/redemptions.go` is reached only
  when `InTx` returns nil, which happens only after `tx.Commit` succeeds (`store/tx.go:97-101`). Replay, 409, 422,
  paused, busy and unknown outcome all return before it.
- **Request context without detachment:** no. `Invalidator.Delete` and `DeleteAll` wrap the context in
  `context.WithoutCancel` with their own deadline; the switch path passes the signal context, detached the same way.
  `Exhausted` uses `spent` from the locked step-4 read, so `spent + awarded == budget` is correct.
- **demo-reset safety:** the `!opts.Demo` refusal comes before `boot.Connect` (unit and integration tests);
  TRUNCATE and the campaign UPDATE run in one `InTx`; the budget is left untouched. The state after a partial failure
  is weak (F1, F3) and the budget-kept assertion is vacuous (F2).
- **Address or driver text:** not in our warn line (fixed text plus keys); the go-redis internal logger does print it
  (F8).
- **Harness FLUSHDB isolation:** fine. Test Redis on 56379 (or `FC_TEST_REDIS_ADDR`), no `t.Parallel`, every state
  test starts with `reset`, no other package uses that Redis.
- **Green-on-first-run tests:** mostly proved by the listed mutations; gaps are F2, F3, F4.

## Verdict

APPROVE_WITH_FINDINGS, all minor. The critical write path is sound: deletes happen only after a confirmed COMMIT,
always on a detached context; a Redis failure never changes the response; no cache read is involved. demo-reset
refuses before connecting and truncates in one transaction. To act on: F2 and F3 (vacuous or missing tests, each with
the mutation that stays green), F1 (state after a partial failure), F4 (records fix in `plans/delivery.md`).
